# Архитектура

## Границы компонентов

`app/bot` принимает Telegram-события, ведёт FSM и формирует сообщения. Middleware открывает сессию БД, регистрирует пользователя и проверяет доступ. Проверка членства в канале включается через `TELEGRAM_REQUIRED_CHANNEL_USERNAME`; пустое значение отключает её.

`app/api` принимает webhook и отдаёт подписки. `app/services` содержит общую бизнес-логику, доступную боту, API и Celery. `app/models` описывает схему SQLAlchemy, а `alembic/versions` — её изменения.

## Основные сущности

| Сущность | Назначение |
| --- | --- |
| User | Telegram ID, роль, баланс, бонусные дни, реферальный код |
| Plan | Цена, срок, валюта, лимит трафика |
| Payment | Провайдер, назначение, сумма, статус, внешние идентификаторы |
| Subscription | Пользователь, тариф, сервер, срок, VLESS UUID, статус |
| VpnServer | Панель 3x-ui, inbound, параметры подключения Reality |
| Promocode | Скидка или бонусные дни, срок и лимит применений |
| Referral | Связь пригласившего и приглашённого пользователей |
| AuditLog | Действие, сущность и дополнительные сведения |

Денежные суммы представлены `Decimal` и `Numeric`, суммы Telegram invoice — в минимальных единицах валюты. Пароль панели хранится в зашифрованном виде. `APP_SECRET_KEY` также используется для шифрования токенов экспорта подписок; его смена требует плана миграции существующих данных и ссылок.

## Покупка подписки

1. Обработчик получает пользователя, тариф и выбранный сервер.
2. `PaymentService` рассчитывает скидку и бонусные дни, сохраняет ожидающий платёж.
3. Пользователь оплачивает Telegram invoice или размещённую платёжную форму ЮKassa.
4. Подтверждённый платёж передаётся в `mark_paid_and_activate`. ЮKassa webhook перепроверяет статус, сумму, валюту и связь с локальным счётом через API провайдера.
5. `SubscriptionService` создаёт или продлевает подписку и синхронизирует клиента в 3x-ui.
6. Обновляются промокоды, реферальные награды и журнал действий. Пользователь получает конфигурацию.

Повторная последовательная обработка уже оплаченной записи не активирует её повторно. Конкурентную доставку событий, ошибки на границе транзакции БД и внешнего API и восстановление после сбоев следует проверять отдельными интеграционными тестами.

## Фоновые процессы

Celery Beat публикует периодические задачи в Redis. Worker проверяет статусы платежей ЮKassa, напоминает об окончании подписки, удаляет истёкших клиентов из панели и обрабатывает исчерпание трафика. Рассылка запускается администратором как фоновая задача.

Внешние операции с Telegram и 3x-ui выполняются по HTTP. Доступность этих систем влияет на завершение пользовательских сценариев.

## Проверки и дальнейшее развитие

Unit-тесты изолируют внешние зависимости. Offline-проверка Alembic строит PostgreSQL SQL для цепочки миграций без подключения к БД. Следующий уровень проверки — интеграционное окружение с PostgreSQL, Redis и тестовыми API, включая параллельные оплаты и восстановление после ошибок панели. Для масштабирования понадобятся наблюдаемость, управление повторными попытками и согласованность внешних операций с транзакциями БД.
